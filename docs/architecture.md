# 架构与方法论

rmtest 的核心不是"又一个检查清单"，而是一套**测试体系设计**。本文记录承重决策与它们要解决的问题。

## 1. 承重决策（锁死，不可倒退）

1. **薄内核**：内核只编排（适配器 → facts → 插件 → 报告），零检查逻辑。检查逻辑全部在插件里。
2. **归一化 IR 只增不改**：插件 manifest 声明 `irVersion`，内核做兼容闸门。IR 只描述"数据驱动 RPG 引擎"的公共概念（地图/事件/条件/开关/资源/传送）。
3. **facts provider 插件化**：新分析维度 = 新 facts + 新消费者，不动全局结构。
4. **类型化报告 section**：未知类型优雅降级，UI 永不被新检查器绑架。

这四条保证：加检查器、加引擎、加分析维度、加报告类型，全部是加法不是重构。

## 2. 测试金字塔

| 层 | 对应物 | 检查器/机制 |
|---|---|---|
| 单元 | 单条目一致性、单事件页隔离执行 | 悬空引用、脸图/图标越界、资源规格 |
| 接口 | 开关/变量的写读契约（RM 没有编译器保护，开关就是接口） | 生命周期 facts → 条件恒假/死逻辑 |
| E2E | 任务链、地图遍历、存档往返 | 场景 DSL + 执行器 + 断言 |
| 回归 | bug 复现场景语料库 | 语料库 + 时效性引擎 |
| fuzz | 随机输入 + 新颖度驱动 | 确定性种子、崩溃捕获 |
| 视觉回归 | 关键帧截图 diff | golden 基线 + 像素 diff |

**缺陷尽可能在低层截获**：静态层天然 100% 覆盖，覆盖度管理的压力只在动态层。

## 3. 覆盖度：分母决定成败

覆盖率 = 已命中 / **静态可达集**（不是"全部内容"）。可达集由传送图 + 事件条件分析给出：

- 可达但未命中 → 测试缺口（列入报告）
- 不可达 → 它本身就是 bug 报告，不构成覆盖义务

补测三引擎：**求解器**（确定性 BFS 合成场景）→ **fuzz**（新颖度驱动探索）→ **AI**（求解器卡住时兜底，见 §6）。

## 4. 时效性：三分类而非二值

每个场景携带绑定指纹（内容哈希）。每次对当前游戏数据校验：

- **fresh**：指纹一致 → 跑
- **broken**：硬引用悬挂 → 不能跑；要么场景删，要么游戏丢了内容（bug）
- **stale**：引用可解析但内容变了 → 能跑但断言意图可能漂移，标可疑

**机械重链**：broken 引用用内容哈希在全库搜唯一匹配，自动迁移绑定（v1 仅地图，文件哈希粒度天然；开关/变量的个体粒度哈希是后续工作）。

**人只在四处介入**：基线审批、重链确认、stale 终审、误报标记。其余全自动。

## 5. 显示问题：三层漏斗

1. **数据/状态层（确定性）**：全屏黑 = 屏幕状态对象；卡墙 = passability 数据；溢出 = 字体度量计算；空脸图 = 索引越界。大部分"显示 bug"根本不用看像素。
2. **像素层（确定性）**：headless 截图 + 全黑/全白检测 + golden diff——只判"客观坏"和"变了没有"。
3. **AI 视觉抽检 + 证据画廊（人眼兜底）**：工具不替代人眼，而是把"需要人看的东西"从全部压缩到按异常度排序的一小撮。

## 6. AI 层（路线图）：沙漏结构

AI 只做翻译，不做判定：

```
自然语言 ──→ [AI] ──→ 场景 DSL ──→ [校验闸门] ──→ [确定性执行器] ──→ 通过/失败
                    ↑失败回喂（带具体错误）                       │
                    失败轨迹 ──→ [AI] ──→ bug 报告翻译
```

三条机制钉死边界：窄接口契约（AI 没有"帮我找 bug"端点）、校验闸门（引用必须真实存在，非法打回重写）、判定隔离（AI 不读执行器内部，bug 是引擎找出来的）。核心引擎永远确定性，AI 挂了产品照跑。

## 7. 坏数据容错

用户的游戏本来就是有 bug 的——分析器必须吃坏数据不崩：

- 解析器字段级守卫，坏文件记 warning 不抛异常
- 内核 per-checker try/catch，单插件崩溃只降级该插件结果
- 报告标注"分析不完整"而非白屏

## 8. 可复现性

- fuzz 确定性种子（mulberry32）
- 场景绑定记录游戏内容指纹 + 引擎版本
- 每次运行结果入项目库（SQLite），历史可查

## 9. 插件分发

Checker 插件是**单文件 ES 模块**（见 `examples/checkers/sample-checker.ts`）。分发 = 分享文件：

1. 作者写一个 checker 文件（默认导出 `CheckerPlugin` 或数组）
2. 用户放到任意目录，`loadCheckersFromDir(dir)` 动态加载
3. manifest 声明 `irVersion`，加载时做兼容闸门；坏插件隔离不炸加载器

无需发布平台、无需版本管理器——文件级分发对社区场景最直接。插件内嵌 fixture 回归资产的约定见 roadmap。
